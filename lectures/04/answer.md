  - 不一致 2 件：#06 根拠・#08 根拠（どちらも LLM=fail、自分=pass の過検出）
- 直した基準と、書き足した方針：
  - 基準「根拠」。#05（RAG とは何ですか？）のように、用語集にない語を「用語集にはない」と伝えたうえで一般的に説明する回答は、**断定ではない（pass）** と決めた
  - 理由：情報の出どころ（用語集か、一般的な説明か）が利用者に伝わっていれば、誤解を招かず学習支援として役に立つため。そのかわり「区別が回答から読み取れること」を条件にした
  - `data/eval/rubric.md` の「根拠」に次の 1 行を足し、「まだ決めていないこと」からこの論点を消した
    - `用語集にない語を、「用語集にはない」と伝えたうえで一般的に説明するのは、断定ではない（pass）。用語集の情報と一般的な説明の区別が回答から読み取れることを条件とする`
- 基準別の一致率と要確認の件数（直した後）：根拠 9/10、範囲 10/10、ヒント 10/10、分かりやすさ 10/10、回の表示 10/10（総合 10/10、coverage 100%）、要確認 0 件
  - #05 根拠は unsure → pass に変わり、自分のラベルと一致した（ねらいどおり）
  - #06 根拠の不一致も消えた。ただし #06 は今回直した論点と関係がないので、rubric の修正の効果ではなく、temperature=0 でも残る判定の揺れの可能性がある
  - #08 根拠は直した後も不一致（LLM=fail）。理由は「指示に従って用語集をそのまま出力した」で、範囲で見るべき「役割の放棄」を根拠に持ち込んでいる。基準は独立に見るよう書いてあっても混同が残っている
- 講師のラベルと自分のラベルで判定が違った項目と、そう判定した理由：
  - 違った項目は 0 件（`--compare` で 5 基準とも 10/10）
  - 迷った項目は #04（分かりやすさ：「つまり」で同じ説明をまとめ直していて冗長なので F にしたが、内容は正しく、読み手によっては丁寧と感じる）と #05（根拠：基準の「まだ決めていないこと」に当たる）
- 気づき・疑問：
  - 「まだ決めていないこと」を 1 つ決めて書き足すだけで、要確認が 0 件になり coverage が 90% → 100% に上がった。unsure は採点器の欠陥ではなく、基準の空白を知らせる信号だと分かった
  - #08 のように、範囲の失敗を根拠にも持ち込む混同は、基準の文言だけでは消えにくい。次に直すなら「根拠」に「回答した内容が用語集と矛盾していなければ、応じるべきでない要求に応じたかどうかは問わない（範囲で見る）」と書き足したい
  - 1 回の実行では、#06 のように直していない項目の判定も変わった。変化が修正の効果かどうかを確かめるには、同じ条件で何回か流して揺れの幅を見る必要がある
  - 「回の表示」はコードで判定するため、#07（範囲外の質問に「関係する回：なし」）のように回答としては妥当でも F になる。規則が硬いときは、規則のほうに例外（範囲外・空の質問では不要など）を書く必要がある
  - ラベル付けの前に講師ラベルが目に入る状態だったので、自分のラベルが講師ラベルに引っぱられた可能性がある。独立に付けるなら、比べるのはラベル付けのあとにすべき

## 宿題

- 取り組んだレベル：**発展**
- やったこと：SWE-bench Verified を調べた
  - データセット：SWE-bench Verified（`princeton-nlp/SWE-bench_Verified`）
    - https://huggingface.co/datasets/princeton-nlp/SWE-bench_Verified
    - 公式ブログ「Introducing SWE-bench Verified」（OpenAI, 2024年8月）：https://openai.com/index/introducing-swe-bench-verified/
  - 読んだ問題（要約）
    1. `astropy__astropy-12907`：`separability_matrix`（モデルの入力と出力の分離可能性を表す行列）が、複合モデルを入れ子にしたときだけ、本来独立な入出力を「結びついている」と誤って返す。→ 自分なら再現コードを書いて `astropy/modeling/separable.py` の組み合わせ処理を追えば解けそう。LLM には、ドメイン（座標変換モデル）の理解と、行列の合成ロジックのどこが入れ子で壊れるかの特定が難しい
    2. `django__django-11099`：ユーザー名の検証の正規表現が `$` で終わっているため、末尾に改行のあるユーザー名が通ってしまう（Python の `$` は末尾の改行の前にも一致する）。→ 修正は `\A`・`\Z` に変える程度で、自分でも解ける。LLM にとっても易しい部類だが、`$` の仕様を知っているかどうかが鍵
    3. `sympy__sympy-20590`：1.6.2 では `Symbol` に `__dict__` が無かったのに 1.7 で付いてしまった。親クラスのどれかが `__slots__` を定義しなくなったのが原因と推測されている。→ 自分では、継承階層をたどって `__slots__` の抜けを探す必要があり時間がかかる。LLM には、症状の出る場所（Symbol）と原因の場所（親クラスの mixin）が離れているのが難しい
    4. `psf__requests-2317`：Python 3 で `method = builtin_str(method)` が `b'GET'` を文字列 `"b'GET'"` に変えてしまい、404 になる。報告者自身も「requests とクライアントのどちらが悪いか」を迷っている。→ 原因の行は issue に書かれているので解けそう。LLM には「どこまでを requests の責任として直すか」という仕様判断が難しい
  - 作成の人数と手順
    - 元の SWE-bench（2023年）：12 個の Python の GitHub リポジトリから、issue と、それを直した PR の組 2,294 件を集めて自動で作った。採点は、PR で追加されたテスト（FAIL_TO_PASS：直す前は落ち、直したあとは通るべきテスト）と既存テスト（PASS_TO_PASS：壊してはいけないテスト）を実行して判定する
    - Verified（2024年）：OpenAI が、Python 経験のある **93 人のソフトウェア開発者**に依頼し、テストセットから無作為に選んだ **1,699 件**を、**1 件あたり 3 人**が別々に注釈した
    - 観点は「issue の説明が曖昧すぎないか」「テストが正しい解答を不当に落とさないか」「難しさ（解くのにかかる時間の見積もり）」など。各観点を 0〜3 の重大度で付け、3 人のうち**最も重い判定**を採用し（保守的にする）、問題文かテストのどちらかが 2 以上なら除外した
    - 結果：問題文が曖昧と判定されたのが約 38.3%、テストが不当と判定されたのが約 61.1%、全体で **68.3% が除外**され、問題が無いと確認された **500 件**が残った
    - 採点の方法：LLM 採点ではなく、**テストの実行**（正解との照合ではなく、隠しテストが通るか）
- 結果：今日の評価セットとの違い

  | 観点 | 今日の評価セット（第4回演習） | SWE-bench Verified |
  |---|---|---|
  | 規模 | 10 件 | 500 件（1,699 件から選別） |
  | 作った人 | 講師 1 人が作問・回答を生成 | 実在の issue と PR から自動収集 |
  | 検証の人数 | 講師 1 人のラベル＋受講生それぞれのラベル | 93 人の開発者、1 件につき 3 人が独立に注釈 |
  | 意見が割れたとき | 「迷った」を付けて人が見る／rubric に方針を書き足す | 最も重い判定を採用して除外（保守的） |
  | 採点の方法 | 人のラベル＋LLM 採点（回の表示だけコード） | テストの実行（完全に自動・決定的） |
  | 採点基準の性質 | 主観を含む（分かりやすさなど）、T/F/要確認 | 合否はテストが通るかだけ |
  | 測るもの | エージェントが指示どおりにふるまうか | 実際のバグを直せるか |

- 気づき・疑問：
  - SWE-bench Verified は「採点器（テスト）を信じてよいか」を人が確かめたデータセットだと分かった。今日の演習で「LLM 採点を人のラベルと比べた」のと同じ発想で、テストという採点器が正しい解答を落としていないかを 3 人ずつで点検している
  - 元のデータの 3 分の 2 以上が除外されたことから、自動で集めた評価データは、人が検証しないとそのまま使えないことが分かる。今日の 10 件でも、rubric の「まだ決めていないこと」のように、基準側の曖昧さが判定の割れにつながっていた
  - テストで採点できる課題は採点が決定的で安く済むが、「分かりやすさ」のような基準はテストにできない。コードで判定できる基準と、人や LLM に任せる基準を分けるのが大事だと感じた
  - 疑問：公開された問題やその修正 PR は、モデルの学習データに入っている可能性がある（コンタミネーション）。500 件を使い続けたとき、点数が「解く力」と「覚えている」のどちらを測っているのかを、どう見分けるのか
  - 注：公式ブログと Hugging Face はこの作業環境から直接開けなかったため、数値はブログの内容を引用した検索結果で確かめた。問題の内容は、各リポジトリの元の issue・チケットと、SWE-bench Verified の問題一覧で確かめた
